By default, new web pages can be created anywhere in the Site Tree. Keep the site's information architecture in mind when you place a new page — where a page sits determines its URL, its breadcrumb, and how readers find it.

Overview

A page is an instance of a schema. The schema determines which fields authors see, which presentation is applied at publish, and which delivery targets accept the content. The CMS provides three ways to create a page.

Design vs. published

New pages exist only in the design environment until they are checked in and published. Test in your staging target before publishing to production.

Before you begin

  • You have the Author or Site Designer role for the publishing target.
  • The parent page or folder already exists in the Site Tree.
  • You know which schema the new page should use.

Create a page

  1. Select the parent page in the Site Tree.
  2. Click New Page on the Site Toolbar.
  3. Choose a schema, then enter a name.
  4. Click Create — the page is created checked out to you.
  5. Complete the required fields, then check the page in.
Tip

Name pages by their reader-facing title, not their internal purpose — the name becomes the URL segment and the default breadcrumb label.

Ways to create a page

Each entry point creates the same page; they differ in where you start and how much the CMS decides for you.

Reserved characters

The following characters are rejected in folder, page, component, and asset names:

/ \Path separators in the published URLHyphen
? # &Query string and fragment delimitersOmit

' " ;Break XML serialization of the pageOmit

Create a page via the API

Automation and migration scripts create pages through the REST API. The response includes the generated xID.

POST/api/v1/pages
# Create a page under x1240 using the Article schema
curl -X POST https://cms.example.com/api/v1/pages \
  -H "Authorization: Bearer $TOKEN" \
  -d '{ "parentId": "x1240", "schema": "Article", "checkOut": true }'

Authentication

Generate keys on the API keys page in your dashboard. Keys are scoped by type; each type authenticates a different set of endpoints. Send the key as a bearer token:

Authorization header
Authorization: Bearer $TOKEN
Key typePrefixUse for
{{ k.type }}{{ k.prefix }}{{ k.use }}
Server-side only

Admin keys carry write scope across the whole site. Never embed one in client code — proxy through your own backend and store the key as an environment variable.

Rate limits and pagination

  • 1,000 requests per hour per organization for write endpoints; analytics endpoints share a separate 100/hour pool.
  • List endpoints return nextCursor and hasMore. Keep fetching while hasMore is true.
  • Exceeding a limit returns 429 with a Retry-After header.

API referencePages
POST /api/v1/pages v1 · stable

Create a page

Creates a page under the given parent using the specified schema. Returns the created page including its generated xID.

Usage

Use this endpoint when automating content creation — migrations, bulk imports, or CI jobs that scaffold release pages. The page is created in the design environment and must be checked in and published before it appears on a delivery target.

Authorization

Bearer token with the pages:write scope.
